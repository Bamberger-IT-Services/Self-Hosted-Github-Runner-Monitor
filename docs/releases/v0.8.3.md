# Version 0.8.3

**Stand: 15.11.2026 · veröffentlicht am 15.11.2026**

Korrekturen für Forgejo-Runner: Die Abfrage scheitert nicht mehr an Forgejo 17 („Forgejo nicht
erreichbar“, obwohl der Server antwortet) und nicht mehr an einer langsamen Runner-Suche. Dazu die
Vorbereitung auf den neuen Namen des Repositorys auf Forgejo. Handbuch dieser Version:
`https://github.com/Bamberger-IT-Services/Self-Hosted-Github-Runner-Monitor/tree/v0.8.3/docs/handbuch`

## Update
Info › Updates: erst „Jetzt prüfen“, dann „Jetzt auf 0.8.3 aktualisieren“ – oder auf der VM:
`sudo /opt/runner-monitor/aktuell/einrichten.sh aktualisieren`. Mit „Automatisch aktualisieren“
spielt der Monitor es nachts selbst ein. VMs mit Forgejo als Update-Quelle bitte installieren, bevor
das Repository auf Forgejo umbenannt wird (siehe unten).

## Einmalig nach dem Update
Keine Schritte nötig. `MONITOR_UPDATE_FORGEJO_REPO` nicht eintragen, die Vorgabe passt. Offene Dashboard-Fenster einmal neu laden.

## Was ist neu
- Forgejo 17: „Forgejo nicht erreichbar“ trotz antwortendem Server behoben – Läufe nur noch mit Statusfilter und seitenweise (#163)
- Eine zu große oder ungültige Antwort eines Repositorys gilt nur für dieses als „Läufe nicht lesbar“, nicht mehr für die ganze Abfrage
- Die erweiterte Runner-Suche (`/admin`, Listen der Repositories) läuft erst nach Läufen und Jobs und hält die Frist der Runde ein (#151)
- Runner-Erkennung: Ersatznamen (Monitor-ID, Unit) zählen nur in der eigenen Runner-Liste, ein gleichnamiger Runner einer anderen Organisation erscheint nicht mehr (#152)
- Weicht der Server in `runner.json` von dem in `.runner` ab, steht das als Merkmal im Fund; die Begründungen der Funde sind übersetzt
- Update-Quelle Forgejo: neuer Schlüssel `MONITOR_UPDATE_FORGEJO_REPO` für den Namen des Repositorys auf Forgejo (#162)

## Geändertes Verhalten
- Das Repository auf Forgejo heißt künftig `Bamberger-IT-Services/Git-Runner-Monitor-Self-Hosted` (E-33). Das eingefrorene
  GitHub-Repository behält den alten Namen: Updates von GitHub, Herkunftsprüfung, Doku-Links und Release-Adressen bleiben
  unverändert. `MONITOR_RELEASE_REPO` **nicht** auf den neuen Namen setzen, sonst scheitert die Herkunftsprüfung.
- Bei Forgejo als Quelle kommt der Pfad aus `MONITOR_UPDATE_FORGEJO_REPO` (Vorgabe: der neue Name) statt aus
  `MONITOR_RELEASE_REPO`.
- Ein Fund mit abweichendem Server gilt als „wahrscheinlich“ statt „sicher“, auch wenn der Server aus `runner.json` antwortet.

## Reihenfolge der Umbenennung
1. Release 0.8.3 veröffentlichen, VMs mit Forgejo als Quelle auf 0.8.3 aktualisieren – das geht nur vor der Umbenennung
   über Forgejo; 0.8.2 und älter folgen der Weiterleitung des alten Namens nicht.
2. Danach das Repository auf Forgejo umbenennen.
3. Zwischen 1 und 2 meldet eine VM mit 0.8.3 und Forgejo-Quelle „Repository oder Release auf Forgejo nicht gefunden
   (404)“ – erwartet, verschwindet mit der Umbenennung. VMs mit GitHub als Quelle betrifft das nicht.
4. Eine VM, die nach der Umbenennung noch 0.8.2 hat: `einrichten.sh quelle`, „1“ (GitHub), aktualisieren, dann wieder „2“ –
   oder das Paket von Hand installieren (docs/UPDATE.md).

## Bekannt
- Noch nicht vollständig auf einer echten Runner-VM abgenommen; der Statusfilter für Läufe ist bei Gitea nur nach der
  Beschreibung umgesetzt (Rückfall ohne Filter), nicht an einem echten Server geprüft.
- Gitea nur nach der OpenAPI-Beschreibung, GitLab nach der offiziellen Dokumentation umgesetzt.
